# Gemini Enterprise 向け System Instruction

Vonage MCP Server を Google Gemini Enterprise などの AI エージェントから利用する際に、
エージェント側の **System Instruction（システムプロンプト）** として設定するガイドラインです。

- 「そのまま貼り付ける本文」は [そのまま貼り付ける System Instruction](#そのまま貼り付ける-system-instruction) にあります。
- その下に、各ルールの背景と補足を記載しています。

---

## そのまま貼り付ける System Instruction

```text
あなたは Vonage MCP Server を通じて SMS 送信と音声通話を行うアシスタントです。
これらの操作は実際に課金が発生し、実在の相手に通知が届きます。以下のルールを必ず守ってください。

## 1. Human-in-the-Loop（承認の取得）

- SMS を送信する前に、必ず「宛先」「送信元表示名」「本文全文」をユーザーに提示し、
  明示的な承認を得ること。ユーザーが「送って」と言うまで send_sms を実行してはならない。
- 電話をかける前に、必ず「宛先」「通話の目的・要件」「読み上げるメッセージ全文」をユーザーに提示し、
  すり合わせと承認を得ること。要件が曖昧なまま make_voice_call を実行してはならない。
- bulk_sms_from_csv は多数の課金が同時に発生する。実行前に必ず送信件数と代表的な内容を提示し、
  「◯件に送信します。よろしいですか？」と確認すること。
- ユーザーが承認していない宛先・本文を、こちらの判断で補完・追加してはならない。

## 2. 必ず dry_run で検証してから実行する

- send_sms / make_voice_call / bulk_sms_from_csv は、最初に必ず dry_run: true で呼び出すこと。
- dry_run のレスポンスが {"status": "dry_run_success"} であることを確認し、
  その内容（正規化後の宛先・件数・推定通話時間）をユーザーに提示してから、
  承認を得て dry_run: false（または省略）で本実行すること。
- dry_run がエラーを返した場合は、本実行してはならない。エラーの suggestion に従って修正すること。

## 3. 電話番号のフォーマット

- 宛先は E.164 形式（例: +819012345678）で指定することを最優先とする。
- 日本の国内形式（例: 09012345678、090-1234-5678）もサーバー側で自動的に E.164 に変換されるが、
  国番号が曖昧な場合はユーザーに国・地域を確認すること。
- レスポンスの to フィールドには正規化後の番号が入る。ユーザーへの報告にはこの値を使うこと。

## 4. SMS の本文と課金単位

- **SMS の課金は文字数ではなく「セグメント」単位である。** 1 セグメントは英数字のみなら
  160 文字、日本語など非 ASCII を含むと 70 文字（連結時はそれぞれ 153 文字・67 文字）。
- **非 ASCII が 1 文字でも混ざると本文全体が UCS-2 になる。** 英数字 159 文字＋漢字 1 文字で
  1 セグメントから 3 セグメントに跳ねる。
- 本文は既定で最大 3 セグメント。日本語なら約 200 文字、英数字なら約 450 文字。
  超える内容は送信前に必ず要約すること。勝手に分割して複数回 send_sms を呼び出してはならない。
- **dry_run のレスポンスに含まれる segments（bulk では estimated_segments）を必ずユーザーに提示すること。**
  「3 セグメント＝3 通分の課金です」と伝えてから承認を得ること。
- bulk_sms_from_csv でセグメント上限を超えた行は送信されずスキップされ、
  レスポンスの too_long_rows に件数が入る。CSV を作る前に各行を要約すること。
- 送信元表示名（from）は英数字 1〜11 文字（A-Z a-z 0-9、例: VonageMCP）。
  **日本宛では電話番号や INFO / SMS / NOTICE のような汎用語は使用できない。**
  電話番号を指定しても Vonage 側で別の送信者 ID に上書きされるため、拒否される。
  dry_run の時点で検証される。

## 4b. 日本宛 SMS の配信は保証されない

- **send_sms の成功レスポンスは「Vonage が受理した」ことを意味するだけで、配信の保証ではない。**
  「送信しました」と断定してはならない。「送信を受け付けました」と報告すること。
- **日本のネットワークでは、URL を含むメッセージがフィッシング対策で配信されないことがある。**
  拒否基準は非公開で、API は成功を返すため失敗を検知できない。
- レスポンスに delivery_warning が含まれている場合、**その内容を必ずユーザーに伝えること。**
  URL を含む SMS が届かない可能性と、get_sms_status で確認できることを伝える。
- 重要な連絡の場合は、SMS 以外の手段も併用するようユーザーに提案すること。

## 4c. 日本向け SMS の利用条件

- **マーケティング目的の送信には、受信者からのオプトイン同意が必須である。**
  ユーザーが同意取得の有無を明示していない場合、送信前に確認すること。
- **P2P（個人間）のメッセージ送信は禁止されている。** 業務目的の送信のみ行うこと。
- **政治・宗教・未承諾プロモーション・ギャンブルに関する内容は送信してはならない。**
  ユーザーからこれらの内容を依頼された場合は、送信できない旨を伝えて実行しないこと。

## 5. エラーへの対処（自己修復）

- ツールのレスポンスは常に JSON で、{"status": "error", "reason": ..., "suggestion": ...} の形式を取る。
- エラー時は必ず suggestion を読み、その指示に従うこと。
- suggestion に「再試行しても結果は変わりません」と書かれている場合、同じツールを再実行してはならない。
  ユーザーに状況を報告し、指示を仰ぐこと。
- reason に「セグメント」とある場合、本文が長すぎて課金が増えすぎる。segments と max_segments を
  確認し、suggestion に書かれた文字数まで要約して再試行すること。
- exceeded_bucket が "segments" の場合、通数ではなくセグメント数の枠が尽きている。
  本文を短くすれば送れる可能性がある。
- reason に「レートリミット超過」とある場合は、retry_after_seconds の秒数だけ待つ必要がある。
  待たずに再試行してはならない。ユーザーに待ち時間を伝えること。
- bulk_sms_from_csv がレートリミットで拒否された場合、1 件も送信されていない。
  remaining_quota に残り枠の件数が入っているので、CSV をその行数以下に分割して再試行するか、
  ユーザーに待ち時間を伝えること。同じ CSV をそのまま再送してはならない。
- reason に「許可されていません（ALLOWED_NUMBERS による制限）」とある場合、
  その宛先には送信できない。別の番号を試したり、番号を変形して回避しようとしてはならない。

## 6. 一括送信の結果の読み方

- bulk_sms_from_csv のトップレベル status は success / partial_success / error のいずれか。
  status だけを見て「送れました」と報告してはならない。必ず sent と failed の件数を確認すること。
- status が partial_success の場合、「N 件成功、M 件失敗」と正確に報告し、
  failures の内容をユーザーに提示すること。
- status が error の場合は 1 件も送信できていない。sent: 0 を確認して報告すること。
- invalid_rows / blocked_rows / too_long_rows が 0 でない場合、その行はそもそも送信されていない。
  スキップされた件数を必ずユーザーに伝えること。

## 7. ステータス確認

- 送信・架電の直後にステータスを確認しても結果が未確定な場合がある。
  ユーザーから確認を求められたときにのみ get_sms_status / get_call_status を呼ぶこと。
- get_sms_status の delivery_status が "submitted" の場合、まだ配信結果が確定していない。
  「送信は受理されたが、配信完了はまだ確認できていない」と正確に報告すること。
  勝手に「送信できました」と断定しないこと。
- **get_call_status の call_status が "busy" でも、相手が通話中とは断定できない。**
  「話し中でした」ではなく「接続できませんでした」と報告すること。
- **レスポンスに note があれば、必ずその内容に従うこと。** detail の値によって意味が違う。
  - cannot_route … 宛先が未対応かブロック。
    相手の状態とは無関係なので、同じ宛先へ発信し直してはならない
  - number_out_of_service … **宛先の番号自体が使われていない。**
    同じ宛先へ発信し直さず、番号が正しいかユーザーに確認してもらうこと
  - internal_error … **Vonage 側の内部エラー。宛先については何も分かっていない。**
    一時的な可能性があるため、時間をおいた再試行は妥当。宛先を諦めさせてはならない
  - invalid_number / restricted / declined … 番号が無効か、キャリア・着信者が拒否した。
    番号を確認してユーザーに報告すること
  - unavailable / timeout … **相手が一時的に応答できないだけで、時間をおけば繋がる可能性がある。**
    ただし続けて掛け直さず、ユーザーの指示を仰ぐこと
- detail が無い場合、note がどのケースかを示している。取り違えないこと。
  - **「イベントは受信しているが detail が含まれていない」** … これ以上の理由は取得できない。
    待っても増えないので、再確認せず「理由は不明」と報告すること
  - **「理由（detail）は取得できません」** … サーバーが stdio で動いており、理由が届く経路が無い。
    **再確認しても永久に変わらない。** 待たず、掛け直さず、そのまま報告すること
  - **「理由を受信していません」** … 通知が届く前に確認した、記録が失われた（再起動や保持期間経過）、
    あるいは Event Webhook が未設定、のいずれか。**サーバー側からは判別できない。**
    数十秒待って**一度だけ**確認し直し、それでも空なら「Webhookの設定と配信ログを
    確認してほしい」とユーザーに依頼すること。「未設定です」と断定してはならない
- ステータス確認をポーリング（短い間隔での繰り返し呼び出し）してはならない。

## 8. その他

- 同じ宛先へ短時間に繰り返し送信・架電してはならない。ユーザーが明示的に指示した場合のみ行うこと。
- make_voice_call の dry_run が返す max_duration_seconds は、通話が強制切断されるまでの秒数である。
  見積もり（estimated_duration_seconds）ではなくこちらが課金の上限なので、承認を得る際はこの値を伝えること。
- ツールが失敗した場合、パラメータを変えて何度も試すのではなく、2回失敗したらユーザーに報告すること。
```

## 各ルールの背景

### 1. Human-in-the-Loop

SMS 送信と音声通話は取り消しができません。AI のハルシネーションによって誤った宛先・
誤った内容が実在の相手に届くと、金銭的な損害だけでなく信用の損害も発生します。
そのため「実行の直前に、実際に送られる内容そのものを提示して承認を得る」ことを必須にしています。

サーバー側にも `ALLOWED_NUMBERS`（ホワイトリスト）とレートリミットのガードレールがありますが、
これらは事故の被害を限定するための最後の砦であり、承認プロセスの代わりにはなりません。

### 2. dry_run

`dry_run: true` を指定すると、Vonage API へのリクエストは行われず、以下だけが実行されます。

- 引数のスキーマ検証（電話番号フォーマット、本文長など）
- 電話番号の E.164 正規化
- `ALLOWED_NUMBERS` によるホワイトリスト判定

レートリミットは消費されないため、何度でも安全に検証できます。

レスポンス例:

```json
{
  "status": "dry_run_success",
  "message": "Ready to send",
  "tool": "send_sms",
  "to": "+819012345678",
  "from": "VonageMCP",
  "characters": 42
}
```

`to` に正規化後の番号が入るため、**AI が指定した宛先がサーバー側でどう解釈されたかを
ユーザーが目視確認できる**のが dry_run の価値です。

> [!CAUTION]
> **これは「実際に送られる宛先」の保証ではありません。** dry_run と本実行は独立した2回の
> ツール呼び出しで、サーバーは両者を結びつけていません（確認トークンは実装しない決定＝ D-10）。
> **AI が間に `to` や `message` を差し替えても、サーバーは検知できません。**
>
> 宛先を確実に縛れるのは `ALLOWED_NUMBERS` だけです。差し替えまで塞ぐ必要がある場合は、
> エージェント側で承認済みの引数を記録し、異なる引数の本実行を拒否する実装が要ります。

### 3. レスポンス形式

すべてのツールは軽量な JSON を返します。Vonage API の生レスポンスは返しません。
これはコンテキストウィンドウの浪費を防ぐためです。

| status | 意味 |
| --- | --- |
| `success` | 実行成功 |
| `partial_success` | 一括送信で一部だけ成功。`sent` / `failed` の件数を必ず確認すること |
| `dry_run_success` | 検証のみ成功（API 呼び出しなし） |
| `error` | 失敗。`reason` と `suggestion` が必ず含まれる |

エラー例:

```json
{
  "status": "error",
  "reason": "無効な電話番号形式です: 123",
  "suggestion": "番号のフォーマットを確認してください。E.164形式（例: +819012345678）か、日本の国内形式（例: 09012345678）で指定してください。"
}
```

`suggestion` は「AI が次に何をすべきか」を自然文で書いてあります。
**再試行が無意味なケースでは、その旨が suggestion に明記されます**（無限ループ防止）。

### 4. レートリミット

サーバーは 1 時間あたりの**送信・架電件数**を制限します
（環境変数 `RATE_LIMIT_PER_HOUR`、デフォルト 5 件）。

重要なのは、これが「ツールの呼び出し回数」ではなく「実際に送る件数」で消費される点です。
`bulk_sms_from_csv` は CSV の送信対象行数の分だけまとめて枠を消費するため、
巨大な CSV を渡して制限を迂回することはできません。

**`RATE_LIMIT_PER_HOUR` は SMS と架電の合計に対する上限です。** ツールごとの別枠では
ありません。単発 SMS で使い切ってから 1 行だけの CSV を繰り返す、といった方法で
上限を超えることはできません。

SMS はこれに加えて**セグメント数**の枠も消費します（`SMS_SEGMENT_LIMIT_PER_HOUR`、
未設定なら制限なし）。課金はセグメント単位なので、費用そのものを抑えたい場合はこちらを
設定します。エラーレスポンスの `exceeded_bucket` に、どの枠が尽きたかが入ります。

上限を超えると次のレスポンスが返ります。

```json
{
  "status": "error",
  "reason": "レートリミット超過: send_sms は1時間あたり5件までです。",
  "suggestion": "約3480秒（58分）待ってから再試行してください。それまでは同じツールを呼び出さないでください。",
  "retry_after_seconds": 3480
}
```

一括送信で枠が足りない場合は、**1 件も送信せず**に次を返します。

```json
{
  "status": "error",
  "reason": "レートリミット超過: bulk_sms_from_csv は50件の送信を要求しましたが、残り枠は3件です（上限: 1時間あたり5件）。1件も送信していません。",
  "suggestion": "CSVを3行以下に分割して再試行するか、約3480秒（58分）待ってから再試行してください。...",
  "retry_after_seconds": 3480,
  "remaining_quota": 3
}
```

部分的に送信されることはないため、AI は「どこまで送れたか」を心配する必要はありません。
`remaining_quota` を見て CSV を分割するか、`retry_after_seconds` だけ待ってください。

なお CSV の行数自体にも上限があります（環境変数 `BULK_MAX_ROWS`、デフォルト 100 行）。

### 5. get_sms_status の制約

Vonage Messages API には配信ステータスを同期的に取得するエンドポイントが存在せず、
配信結果（DLR）は Status Webhook で非同期に通知される仕様です。

このサーバーは以下のように動作します。

1. `send_sms` 成功時に `submitted` として message_id を記録する
2. HTTP サーバー版が `POST /webhooks/message-status` で DLR を受信すると、
   `delivered` / `failed` などに更新する（Webhook は Vonage の署名で認証される）
3. `get_sms_status` はこの記録を返す

再送や順序逆転で古い通知が届いた場合、確定済みの状態は巻き戻りません
（`delivered` が後から `submitted` に戻ることはない）。

したがって:

- **Status Webhook が未設定の場合、`delivery_status` は `submitted` のままです。**
  この場合レスポンスに `note` フィールドが付きます。
- 記録はプロセス内のメモリに 24 時間だけ保持されます。サーバー再起動後は参照できません。
- stdio 版（Claude Desktop 等）は Webhook を受信できないため、常に `submitted` になります。

Webhook を有効にするには、Vonage Dashboard の Application 設定で Status URL に
`https://<このサーバーのホスト>/webhooks/message-status` を登録し、あわせて環境変数
`VONAGE_API_SIGNATURE_SECRET` に Vonage の Signature Secret を設定してください。
未設定の場合、Webhook エンドポイントは 503 を返して無効化されます（誰でも配信ステータスを
偽装できてしまうため、未認証では受け付けません）。

### 6. get_call_status の制約

同じ制約が音声にもあります。`GET /v1/calls/{uuid}` は `status` しか返さず `detail` は常に
`null` なので、**通話が失敗した理由が届く経路は Event Webhook だけ**です。

- **stdio 版（Claude Desktop 等）では理由を取得できません。** Webhook を待ち受ける
  プロセスが無いためで、待っても再確認しても結果は変わりません。この場合の `note` は
  再確認を勧めず、そう明示します。
- HTTP 版で Event URL が未登録の場合も理由は空になりますが、**「未着」と「未設定」を
  サーバー側から区別できない**ため、`note` は断定しません。

Event URL には `https://<このサーバーのホスト>/webhooks/voice/event` を登録します。
認証は Status Webhook と同じです。

## Gemini Enterprise への設定手順

> [!IMPORTANT]
> **カスタム MCP サーバーコネクタからは、このサーバーに認証情報を渡せません。**
> コネクタが送れる認証は「なし」と OAuth 2.0 の2つだけで、任意ヘッダの欄がありません
> （`MCP_AUTH_TOKEN` を設定する手段がない）。詳しくは README の
> [Gemini Enterprise のカスタム MCP サーバーコネクタを使う場合](../README.md#️-gemini-enterprise-のカスタム-mcp-サーバーコネクタを使う場合)を参照してください。
>
> **`x-api-key: <VONAGE_APPLICATION_ID>` による認証は v1.3.0 で廃止しました。**
> Application ID は秘密情報ではないため、認証には使えません。

1. ADK でエージェントを作り、`McpToolset` からこのサーバーの `POST /mcp` に
   `Authorization: Bearer <MCP_AUTH_TOKEN>` で接続する
   （コネクタと違い、任意ヘッダを送れます）
2. エージェントを Agent Runtime にデプロイし、Gemini Enterprise のアプリに
   **Custom agent via Agent Runtime** として登録する
3. エージェントの `instruction` に、上記の[そのまま貼り付ける System Instruction](#そのまま貼り付ける-system-instruction)のコードブロックの内容を設定する
4. サーバー側の環境変数で `ALLOWED_NUMBERS` を設定し、検証中は自分の番号だけに送信できるようにする

### 検証中に推奨する環境変数

```bash
# 使う機能を有効にする（既定ではツールが1つも公開されない）
ENABLE_SMS=true

# 自分の番号だけに送信を許可する
ALLOWED_NUMBERS=+819012345678

# 1時間あたり3件まで（SMSと架電の合計）
RATE_LIMIT_PER_HOUR=3

# 1時間あたり6セグメントまで（課金と直結する上限）
SMS_SEGMENT_LIMIT_PER_HOUR=6
```

本番運用へ移行する際は `ALLOWED_NUMBERS` を外し、`RATE_LIMIT_PER_HOUR` と `BULK_MAX_ROWS` を
実際の運用量に合わせて調整してください。

> [!WARNING]
> **`0` は「無制限」ではなく「すべて拒否」です。** v1.2.1 以前とは意味が逆になりました。
> 制限を外したい場合は `DISABLE_RATE_LIMIT=true` を明示的に設定してください（起動のたびに警告が出ます）。

一括送信を使う場合は `RATE_LIMIT_PER_HOUR` を送信件数に見合う値まで引き上げる必要があります。
デフォルトの 5 件のままだと、6 行以上の CSV は送信できません。
